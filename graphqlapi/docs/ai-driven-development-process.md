# クリーンアーキテクチャとAI駆動開発プロセスの設計思想

## 1. 目的と概要
本ドキュメントは、本リポジトリの `.ai/` 配下に構築されている「YAML仕様駆動によるAIコーディングエージェント（OpenCode）運用プロセス」について、その仕組みと、オニオンアーキテクチャ（クリーンアーキテクチャ）と組み合わせることで得られるメリットをまとめたものである。

### 背景と課題
AIコーディングエージェントに機能追加を依頼する場合、指示が曖目だと実装範囲が肥大化し、既存コードの意図しない削除・上書きや、プロジェクトの設計パターンから外れた実装が発生しやすい。また、同種の機能（一覧・詳細・編集画面など）を複数ドメインに対して繰り返し実装する際、人間が毎回詳細な指示文を書くのはコストが高い。

### 解決策
「YAML仕様 → Markdown指示書 → AIエージェントへの実行指示」という3段構成のプロセスを採用し、オニオンアーキテクチャの層構造に沿ってSTEP単位でAIに実装を進めさせることで、指示の再現性と安全性を両立させている。

---

## 2. プロセスの構成

```
.ai/
├── README.md     … 「YAML→指示書」を生成させるためのプロンプト（OpenCodeに渡す）
├── features/      … 機能ごとの要件をYAMLで定義する（人間が書く「要求」）
├── templates/     … 指示書のテンプレート（新規ドメイン作成用／既存ドメイン拡張用）
└── instructions/  … YAMLとテンプレートを合成して生成された、実行可能なMarkdown指示書
```

### フロー

1. **`features/` にYAMLを記述する**（例: `body_composition_edit.yaml`）
   `DOMAIN_NAME` や `OPERATION_TYPE`（List / Create / Show / Edit）といった変数、`FRONTEND_UI_SPEC`（画面構造・デザインテーマ・表示項目）、`BUSINESS_LOGIC_DETAILS`（業務ロジック要件）を宣言的に定義する。既存の `nutrients` ページをデザインの参照元（`design_base_file`）とする運用になっている。

2. **`README.md` のプロンプトをOpenCodeに渡す**
   - OpenCodeが対象ドメインが「新規作成」か「既存拡張」かを判断し、テンプレートを1つ選択する。
   - テンプレート内の `{{変数}}` をYAMLの実値に置換する。
   - `.ai/instructions/` に実行可能な指示書（例: `body_composition_edit_instruction.md`）を出力する。

3. **生成された指示書に従ってOpenCodeが実装を実行する**（STEP0〜7の厳密な順序）

### 指示書の実装順序 — Outside-In / API-First

オニオンアーキテクチャを前提に、常に **GraphQLの型・Resolver（モック）を先に作り、フロントから繋ぎ、最後にDBまで内側へ掘っていく** という進め方を取る。

| STEP | 内容 |
| :--- | :--- |
| STEP 0 | GraphQL Input/Output型 + Resolverのモック実装 + テスト → `yarn codegen` でフロント型生成 |
| STEP 1 | フロント実装（モックデータで画面確認） |
| STEP 2 | フロントとGraphQLエンドポイントの実接続 |
| STEP 3 | Service層のDto / Entity / Interface / モック実装 |
| STEP 4 | PresentationMapperでResolver↔Service結合 |
| STEP 4.5（新規ドメインのみ） | DIコンテナ（`GraphqlContext`, `PrismaAdapter`）への登録 |
| STEP 4.8 | Resolverの本実装（モック撤廃） |
| STEP 5 | Repository層のInterface / モック実装 |
| STEP 6 | Service本実装（業務ロジック組み込み、Repository接続） |
| STEP 7 | RepositoryMapper + Prismaによる本実装 |

既存拡張用テンプレート（`function_extend_domain_template.md`）には、各STEPに「既存のコードやメソッドを決して削除・上書き破壊しないこと」「新しい実装は末尾に追記すること」という制約が明示されており、新規作成用テンプレートとの主な差分はこの破壊防止ルールの有無である。また各ファイルには常に `MealResolver.ts` や `MealService.ts` など既存実装を**リファレンスサンプル**として指定し、ドメインが増えてもコードパターンを揃える設計になっている。

## 3. クリーンアーキテクチャ × AI駆動開発のメリット

### 3.1 AIの実装範囲を「層」で閉じ込められる
オニオンアーキテクチャは責務ごとにファイルが分離されている（Resolver / Service / Repository / Entity / Mapper）ため、AIに対して「このファイルだけ編集してよい」という指示を出しやすい。STEP0〜7で1層ずつ進める設計により、AIが一度に広範囲を書き換えて予期せぬ副作用を起こすリスクを大幅に減らせる。

### 3.2 モックファースト（API先行）でフロント／バックを並行・早期に検証できる
STEP0で型とResolverのモックを先に作り、STEP1でフロントがすぐにモックデータを表示して確認できる。AIが生成したコードが「動くかどうか」を各STEPの終わりに毎回目視確認できるため、エラーの発見が後工程まで持ち越されない。クリーンアーキテクチャの「インターフェース定義→実装」という性質と、AIのステップ実行がうまく噛み合っている。

### 3.3 既存コードの破壊を防ぐガードレールを明示できる
レイヤーが分離されているからこそ、「このインターフェースに1メソッドだけ追記する」といった粒度の小さい指示が可能になる。テンプレートに繰り返し記載された「既存メソッド・importを削除しない」「末尾に追記する」という制約と組み合わせることで、AIの暴走（既存実装の削除・上書き）を構造的に防止できる。

### 3.4 YAML仕様→指示書という中間表現が「要求のブレ」を防ぐ
人間はYAMLで宣言的に要件（フィールド、業務ロジック、デザインテーマ）を書くだけで済み、OpenCodeがテンプレートに流し込んで詳細な指示書（STEP単位の実行計画）を自動生成する。これにより次のような効果が得られる。

- 毎回同じ構造・同じ品質の指示書が得られる（**再現性**）
- `MealResolver.ts` のような既存実装を「リファレンスサンプル」として強制参照させることで、ドメインが増えてもコードパターンが揃う（**一貫性**）
- 非エンジニアでもYAMLの変数を変えるだけで新規機能の指示書を量産できる（**スケーラビリティ**）

### 3.5 各層が独立してテスト可能 → AIの自己検証ループが機能する
Resolver / Service / Repositoryそれぞれに `__tests__` とテスト実行コマンドが明記されており、依存が抽象（Interface）越しになっているためモックへの差し替えが容易である。AIが各STEPの後に自分でテストを実行し、次のSTEPに進む前に壊れていないか確認できる、という「AIが自己検証しながら進む」運用が成立している。

---

## 4. 総括
クリーンアーキテクチャ自体が持つ「関心の分離・依存の逆転」という特性が、AIエージェントに対して **「一度に見るべき範囲」「触ってよい境界」「検証すべき単位」** を明確に区切る役割を果たしている。そこにYAML仕様→テンプレート→STEP実行という定型プロセスを組み合わせることで、AIが安全かつ再現可能に機能追加を遂行できる仕組みになっている。
